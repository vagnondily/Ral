## Vérification du lot 6a
- [high] Viewers can still read exact household GPS pairs through the calculated-field preview — where: server/src/modules/monitoring/monitoring.routes.js:358 (POST /forms/:id/calc-fields/preview, no WRITE guard) -> monitoring.repository.calcPreview:1893 -> calcFields.previewCalc (samples[].inputs) — evidence: Logged in as a viewer (role 'viewer', created on the dev copy), I sent POST /api/monitoring/forms/fc316caf…/calc-fields/preview with {"kind":"expression","expression":"[@_HHCoord_latitude] + [@_HHCoord_longitude]"}. It returned samples such as {"inputs":{"@_HHCoord_latitude":-24.7840622,"@_HHCoord_longitude":45.1925514}}: 8 exact household positions per call, plus a top-10 distribution. With only the latitude it returns 300 rows (296 distinct values). The lot claims that precise points are reserved to admin/manager and that GPS is removed for other roles, but stripGps is only applied in GET /forms/:id/submissions, so the rule is bypassed. — fix: For roles other than admin/manager, run the preview sample rows through submissionGps.stripGps before previewCalc (and the indicator preview/explain, which returns value distributions), or refuse references to GPS_KEY_RE keys. Add a route test: a viewer preview never returns a coordinate with more than 2 decimals.
- [medium] Viewers receive commune centres at 6 decimals, and a median can be one household's exact position — where: server/src/modules/map/geoStats.js:66 publishedPosition (precise when n >= SNAP_BELOW=5); mapPoints.js; test/mapRoutes.test.js:99 only covers n=3 — evidence: As a viewer, GET /api/map/points?from=2026-01&to=2026-10 returned 7 communes at 6 decimals, e.g. Sihanamaro n=5 at -25.192399, 45.778324 and Tsiatosika n=7 at -21.203134, 48.225018. The medians are taken per axis with percentile_cont, so an odd small n can return a real household's lat and lng together. On the dev copy, 2 of the 17 communes with n >= 5 (MG51507230 n=5, MG52516014 n=7) have a median exactly equal to one submission's (gps_lat, gps_lng). The summary says other roles and exports get a 2 km grid, and the test is named 'jamais plus de 2 décimales', but its fixture has no n >= 5 case. — fix: For non-precise roles and in buildExportSvg, snap every derived and commune position to the 2 km grid regardless of n, or publish a snapped mean. Extend the route test with n >= 5 commune and derived positions.
- [medium] After 'Ouvrir la carte' with a multi-month period, the Couverture page shows two different coverage values and a misleading period — where: web/src/pages/dashboard/DashboardCoveragePage.jsx (periodOverride from mems.map.open; MonthSelect, PeriodBanner and the Overview tile keep using `month`) — evidence: With period Jan–Oct 2026 on Vue d'ensemble (compact map: 1,6 %, 21 sites réalisés / 1 280), I clicked 'Ouvrir la carte'. - [medium] The claim 'un ré-import identique ne recalcule plus rien' is false: BEFORE INSERT evaluates the GPS rule on every row — where: server/src/db/migrations/061_map_geo.sql (trg_mon_sub_gps BEFORE INSERT OR UPDATE; early return only for UPDATE) + monitoring.repository.js:1181 INSERT … ON CONFLICT DO UPDATE — evidence: On the dev copy, with track_functions='all', I replayed the import upsert (ON CONFLICT (form_id, external_id) DO UPDATE SET data = …) with identical data. pg_stat_xact_user_functions shows mems_submission_gps calls = 562 and mems_submission_gps_fill = 1124. It took 420 ms, against 59 ms for the same statement with the trigger disabled (×7). PostgreSQL fires BEFORE INSERT row triggers before it checks for conflicts. Commit e9b863a's '562 lignes en 51 ms' was measured with a plain UPDATE, not the import path. — fix: Remove INSERT from the BEFORE trigger. Fill the GPS in an AFTER INSERT row trigger (it fires only for rows actually inserted; the conflict path goes through the UPDATE trigger, which already skips unchanged data), or in one set-based UPDATE of the inserted ids after the import loop. Correct the commit claim and the journal entry.
- [medium] Over the performance budget at 10k sites; /points recomputes the full site × month facts query — where: server/src/modules/map/map.repository.js factsByZoneTx and siteStatusesTx (pointsData) — evidence: I copied the registry ×8 (10 240 sites, 122 880 activation-grid rows for 2026, visits copied) on a 4-core machine with load ≈ 0.8. map.service.districts: p50 246 ms (1 month), 418 ms with max 475 ms (12 months, budget ≤ 400 ms), 524 ms (24), 677 ms with max 843 ms (36 months, which the API allows). factsByZoneTx alone takes 516–527 ms at 12 months and 633–957 ms at 36. map.service.points: 497 ms (12 m) and 809 ms (36 m), because siteStatusesTx runs the whole siteMonthFactsCtes again only to colour 26 GPS sites. One map view therefore runs the facts query twice. Without the grid the ×8 numbers are 347 / 496 / 623 ms. No ×8 measurement appears in the commits or the journal. — fix: In /points, restrict the facts CTE to sites that have a GPS or derived position (join reg first), or reuse the facts already computed. Profile the six-set GROUPING SETS over per_site (HashAggregate ≈ 360 ms at ×8). Record a ×8 run of bench-map in the journal and keep the 36-month case within budget, or lower MAP_MAX_SPAN.
