- [medium] RBM 'sites à planifier' count and 'Générer depuis le RBM' now disagree for any past month — where: server/src/modules/tpm/field.routes.js GET /rbm/sites (asOf = p.to also for legacy ?month=); field.repository.js generateFromRbmTx → rbmSitesTx without asOf; web RbmPage.jsx (MonthSelect) and FieldVisitsPage.jsx:78/202 ('même règle que « Générer »') — evidence: readPeriod turns ?month=M into {from:M,to:M}, and the route then sets asOf = M, so the legacy calls from RbmPage and FieldVisitsPage now get a state bounded at M. Add a test: for a past month, the toPlan count from /rbm/sites equals the number of visits /rbm/generate creates.

- [medium] Server maximum spans (24 / 12 months) are not reflected in usePeriod, PeriodSelect or lib/period (60 months) — where: web/src/lib/period.js (MAX_SPAN 60, readHashPeriod, readSessionPeriod), web/src/components/PeriodBanner.jsx usePeriod (no maxSpan), PeriodSelect default maxSpan=60; server monitoring.routes.js ANALYSIS_MAX_SPAN=24, LIST_MAX_SPAN=12; field.routes.js FACTS_MAX_SPAN=24, VISITS_MAX_SPAN=12 — evidence: In a Playwright harness, opening #/x?from=2022-01&to=2026-10 makes usePeriod return {from:'2022-01', to:'2026-10'} (58 months) and write it to sessionStorage['mems.period.v1']. That session period is shared with the Synthèse, Couverture & performance, Résultats and the budget screens (which allow 60 months per the decisions). The server rejects anything over 24 months: GET /api/monitoring/overview?from=2024-01&to=2026-01 → 400 {code:'period_span', maxSpan:24, span:25}, and the same for field/summary. Once C11–C13 connect the screens, a shared link or a period chosen on Consolidation will make the analysis screens fail with 400. — fix: Give usePeriod a maxSpan option. When a URL or session period is longer than the screen's cap, ignore it and use the screen's default, and say so. Pass the same cap to PeriodSelect. Export the caps from one module that both client and server read, or return the limit from /monitoring/periods.
